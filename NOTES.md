# Why

- There are three users. `admin` installs and updates. `dev` runs the agents: a standard user, so it can't use sudo. `stats` only shows the dashboard. Home folders are private, so `dev` can't read the other users' files.
- `dev` only logs in over Tailscale SSH. Its password is random and nobody knows it, and it has no secure token, so the agents can never get a session at a screen or unlock FileVault. The same goes for `stats` on every Mac mini but mini-1.
- FileVault encrypts the disk, so no one can read the data on a stolen Mac mini. After a power cut, someone unlocks it at the Mac mini: `stats` on mini-1, so the dashboard comes back, `admin` on the others.
- Remote Login stays off (the macOS default) and the firewall blocks all incoming connections. Tailscale is the only way in, for SSH and for Screen Sharing (`tailscale serve`), and your Tailscale login decides who gets in. Screen Sharing turned on from the command line refuses logins, and System Settings can't turn it on while the firewall blocks all incoming connections. So setup.sh asks you to turn it on just before it blocks them. Screen Sharing stays on, and `tailscale serve` reaches it from the Mac mini itself, which the firewall doesn't block.
- Tailscale comes from Homebrew, not the App Store. The App Store app needs a logged-in user. The Homebrew one runs as a system service, so it is up before anyone logs in. It is pinned so that `brew upgrade` can't cut you off. Update it at the Mac mini.
- The Mac minis are tagged in Tailscale. Tagged devices have no key expiry and don't belong to your account. The policy lets only you, from a Mac, log in as `dev`, or as `admin` after you log in to Tailscale again in the browser. mini-1 may log in to the others only as `stats`.
- On every Mac mini but mini-1, the shell of `stats` is `mini-stats`, so logging in as `stats` prints its numbers as JSON and exits.
- The dashboard is `dashboard.html` in Chrome, full screen, on mini-1. It lists the devices tagged `tag:mini`, so a new Mac mini shows up on its own. It shows six at most, in two rows of three once there are more than three.
- Every 5 seconds, `dashboard-data.sh` writes each Mac mini's numbers to `data.js`. The page shows them as text, never as HTML.
- The dashboard screen is 1280×400. macOS refuses desktops under about 540 pixels tall, so it sends 1920×1080 and the screen squashes it. The page is laid out at 1280×400 and stretched to fill the window, which cancels the squash.
- Nobody can answer a dialog at the dashboard screen. `setup.sh` runs Gatekeeper's check on Chrome and checks that it is Google's, then removes its quarantine, so Chrome's first start asks nothing. Chrome starts in kiosk mode, which shows no restore prompt after a power cut, and with a flag that skips Keychain access.
- Wi-Fi is off: the Mac minis use Ethernet.
- The dashboard screen connects to mini-1 by HDMI only and takes USB power from the power strip, so it can't act as a keyboard.
- macOS updates restart the Mac, so you install them yourself, with `-R` or `fdesetup authrestart`, which unlock FileVault once on the way back up.
- The agents push with a `gh` token for Owen's GitHub account. It has the `repo`, `read:org`, `gist`, `workflow`, `admin:ssh_signing_key` and `user:email` scopes, so the agents can change workflow files too. Each Mac mini signs its commits with its own key, so GitHub shows them Verified. The `main` ruleset ([GITHUB.md](GITHUB.md)) makes every change go through a pull request that someone else approves, and secrets reach only jobs on `main`.
- `ssh -a` keeps your laptop's SSH keys out of the Mac minis.
- Claude Code sends no usage data or error reports to Anthropic (`DISABLE_TELEMETRY` and `DISABLE_ERROR_REPORTING` in the managed settings, below). It still updates itself, which `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` would stop, and nothing else updates Claude Code on the Mac minis.
- Each Mac mini has two Claude setups, `claude-work` and `claude-personal`, which can use different accounts. Each keeps its login, connectors and history in its own folder, `~/.claude-work` or `~/.claude-personal` (`CLAUDE_CONFIG_DIR`). The status line starts with the setup's name, and the dashboard shows both. Plain `claude` prints the two commands instead of starting.
- Both setups belong to `dev`, so an agent in one setup can use the other's login and connectors.
- Both setups share one settings file, `/Library/Application Support/ClaudeCode/managed-settings.json`. Only `admin` can change it, so the agents can't turn telemetry back on or disable the candix plugins in their settings.
- `setup.sh` clones candix-com/skills to `~/.candix-skills`, and both setups load the plugins from it in place. Every 5 minutes a job resets the clone to the skills repo's `main` on GitHub, so each new session runs the latest skills, and an edit or branch left there doesn't last. It is no guard against the agents: the clone belongs to `dev`, like the Claude program itself. Work on the skills in another clone.
- `umask 077` makes the files the agents create readable only by `dev`.
- macOS has no Docker daemon, so Colima runs one in a Linux VM, as `dev`, from boot, with nobody logged in. Docker Desktop would run only while someone is logged in at the screen. Each repo starts its own services, such as Postgres, with `docker compose`, the same way as on a laptop, in CI and in Claude's cloud sessions.
- Testcontainers for Node ignores Docker contexts, so `~/.zshenv` sets `DOCKER_HOST` to Colima's socket, and every repo whose tests start their own containers finds Docker with no setup of its own. `docker` and `docker compose` follow `DOCKER_HOST` too, and it names the same socket as Colima's context.
- There are no backups. The code lives on GitHub.
